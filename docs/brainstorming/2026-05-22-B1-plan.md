## Goal

Make the database schema consistent with `data/pricing.ts` so that:
1. The Stripe webhook can persist a purchase for any of the 13 current SKUs without hitting a CHECK violation.
2. The `businesses` table uses the same tier vocabulary as `data/pricing.ts` (no more `premium` ghost value).
3. A purchase can be linked to a specific business (FK), unblocking per-listing revenue queries.

**Non-goals (deferred to B2–B4):**
- Wiring the webhook to actually populate `business_id` or update `businesses.tier`.
- Adding `trial_period_days` to checkout sessions.
- Changing what's rendered publicly on `/local/[industry]`.

## Files to create

### `supabase/migrations/019_purchases_tier_widen.sql`

Two changes:
1. Widen `purchases.tier_slug` CHECK to include all 13 current pricing SKUs.
2. Add `purchases.business_id uuid` nullable FK to `businesses(id)` with `ON DELETE SET NULL` + index.

```sql
-- Hilton Ahead: widen purchases.tier_slug CHECK to current pricing catalog
-- and link purchases to businesses for per-listing revenue queries.
--
-- Builds on migration 009_purchases.sql.
--
-- Background: data/pricing.ts now defines 13 tier slugs across B2C, B2B,
-- and B2B-Ads. The original 009 CHECK only allowed 6. New SKUs added since
-- (heritage-kit-vip, insider-club-*, all 4 ad tiers) would fail the CHECK,
-- causing the Stripe webhook to throw on checkout completion.
--
-- The business_id column makes the relationship from a B2B purchase to the
-- business listing explicit. Today the only link is by lower(email) match,
-- which is fragile. B2 will populate this column on webhook receipt. For
-- now it remains nullable and unpopulated — pure schema groundwork.
--
-- Idempotent.

-- 1) Widen tier_slug CHECK to the current catalog.
alter table public.purchases
  drop constraint if exists purchases_tier_slug_check;

alter table public.purchases
  add constraint purchases_tier_slug_check
  check (tier_slug in (
    -- B2C
    'compass',
    'charter',
    'heritage',
    'heritage-kit-vip',
    'insider-club-monthly',
    'insider-club-yearly',
    -- B2B (directory)
    'listed',
    'featured',
    'signature',
    -- B2B-Ads (direct display)
    'featured-pin',
    'story-sponsor',
    'page-display',
    'featured-villa'
  ));

-- 2) Link purchases to businesses (nullable; populated by webhook in B2).
alter table public.purchases
  add column if not exists business_id uuid
  references public.businesses(id) on delete set null;

create index if not exists idx_purchases_business_id
  on public.purchases(business_id);
```

### `supabase/migrations/020_businesses_tier_align.sql`

Three changes:
1. Drop existing CHECK on `businesses.tier`.
2. Migrate any `premium` rows → `signature` (data fix before re-applying CHECK).
3. Re-add CHECK with the new vocabulary `('free', 'listed', 'featured', 'signature')`.

```sql
-- Hilton Ahead: align businesses.tier vocabulary with data/pricing.ts.
--
-- Builds on migration 017_business_portal.sql.
--
-- Background: 017 defined businesses.tier as ('free', 'featured', 'premium').
-- The 'premium' value was the original name for the top tier; data/pricing.ts
-- now calls it 'signature'. Also, there's an entry-paid tier ('listed' at
-- $600/yr) that has no value in the schema.
--
-- This migration renames premium → signature in-place and adds 'listed'.
-- The 'featured' value keeps its name. Default stays 'free'.
--
-- Order: drop CHECK → migrate data → re-add CHECK. Doing the UPDATE before
-- dropping the CHECK would fail because 'signature' isn't yet allowed.
--
-- Idempotent.

alter table public.businesses
  drop constraint if exists businesses_tier_check;

update public.businesses
  set tier = 'signature'
  where tier = 'premium';

alter table public.businesses
  add constraint businesses_tier_check
  check (tier in ('free', 'listed', 'featured', 'signature'));
```

## Step-by-step

1. **Pre-flight: confirm no rows would fail the new CHECKs.**
   - In Supabase SQL editor (or local DB):
     ```sql
     -- Should return 0 rows. Anything here would block migration 019.
     select tier_slug, count(*)
     from purchases
     where tier_slug not in (
       'compass','charter','heritage','heritage-kit-vip',
       'insider-club-monthly','insider-club-yearly',
       'listed','featured','signature',
       'featured-pin','story-sponsor','page-display','featured-villa'
     )
     group by tier_slug;

     -- Should return only 'premium' (or nothing). Migration 020 handles 'premium'.
     select tier, count(*)
     from businesses
     where tier not in ('free','listed','featured','signature','premium')
     group by tier;
     ```

## Risks + mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Prod has a `purchases` row with an unknown `tier_slug` (e.g. orphaned from a deleted SKU) | Med | Pre-flight query in step 1. If found, decide: update to a valid slug, or add to the new CHECK as a legacy value. |
| Prod has a `businesses.tier` value other than `'free' \| 'featured' \| 'premium'` | Low | Migration 017 already enforced the CHECK; impossible unless someone bypassed it via service role. Pre-flight query confirms. |
| `business_id` FK rejects existing rows | None | Column added nullable, no default — existing rows get NULL. |
| Order of operations on 020 fails | Med | The plan drops CHECK before UPDATE before re-adding CHECK — that's the correct order. Verified mentally above. |
| Vercel deploy fires mid-migration on prod | Low | Schema changes are backward compatible. Old app code (using `premium`) would still write `premium` and fail the new CHECK — but no live writer uses `premium`. Search-confirmed in the audit. |
| Late-discovered third CHECK bug (e.g. some other table) | Low | This plan touches only `purchases` and `businesses`. If discovered, file as B1.5 or fold into B2 — don't expand B1. |

## Rollback plan

If 019 lands but 020 fails (or vice versa):

### Rollback 019
```sql
alter table public.purchases drop constraint if exists purchases_tier_slug_check;
alter table public.purchases
  add constraint purchases_tier_slug_check
  check (tier_slug in ('compass','charter','heritage','listed','featured','signature'));

alter table public.purchases drop constraint if exists purchases_tier_audience_check;
alter table public.purchases
  add constraint purchases_tier_audience_check
  check (tier_audience in ('b2c','b2b'));

drop index if exists idx_purchases_business_id;
alter table public.purchases drop column if exists business_id;
```

### Rollback 020
```sql
alter table public.businesses drop constraint if exists businesses_tier_check;
update public.businesses set tier = 'premium' where tier = 'signature';
alter table public.businesses
  add constraint businesses_tier_check
  check (tier in ('free','featured','premium'));
```

**Caveat on 020 rollback:** if any rows were created AS `signature` after the migration (not migrated from `premium`), they would be incorrectly rolled back to `premium`. Mitigation: rollback ASAP if needed, before any new `signature` rows are written. Acceptable risk because B2 isn't writing `signature` yet — only B1 lands here, no new writers active.
